# 01-业务需求与系统总体设计

上一章准备了开发环境和项目目录。本章开始理解商城的业务：谁会使用系统、他们要完成什么操作，以及这些操作需要记录哪些信息。这些认识将作为下一章“数据库概念模型与逻辑设计”的输入。

本章根据项目教程第 01 章整理，沿着“业务场景 → 角色与用例 → 数据需求 → 系统总体结构”的顺序展开。

## 一、系统要解决什么问题

### （一）从一次购物和一次经营理解系统

买家进入商城，浏览和搜索商品，选择具体规格并加入购物车。确认购买时，买家按店铺提交订单，系统确定成交金额、扣减库存并保存收货信息。随后，买家支付，商家发货，买家确认收货；如果尚未支付，买家也可以取消订单，由系统归还库存。

商家负责维护本店商品、规格、售价和可售库存，查看本店订单并处理发货，还需要了解一段时间内的销售情况。

商城另外提供两项辅助功能：智能导购根据公开商品与资料回答选购问题；经营分析根据当前店铺的销售统计提供解释和建议。

### （二）当前版本的范围

本版本围绕“商品展示—购物车—下单—支付—发货—收货”完成基本交易流程，同时提供店铺经营和 AI 辅助功能。买家可以自行注册；商家账号及店铺由系统初始化建立。支付和发货采用模拟方式，退款、退货以及真实支付和物流对接不在本版本范围内。

一笔订单只属于一家店铺。买家可以在购物车中放入多家店铺的商品，但需要按店铺分别下单。

## 二、角色与用例

### （一）角色

| 角色 | 主要目标 | 可以访问的数据范围 |
| --- | --- | --- |
| 访客 | 浏览和搜索商品、查看详情、注册买家账号 | 已上架商品及公开品类 |
| 买家 | 登录、管理购物车、提交和查看订单、支付、取消、确认收货、咨询选购建议 | 本人购物车与订单、公开商品与资料 |
| 商家 | 登录、管理商品与 SKU、查看本店订单、发货、查看统计与经营分析、咨询选购建议 | 本店商品、订单与经营数据、公开商品与资料 |

买家和商家都拥有登录账号，图中用“商城用户”概括二者共有的角色。这里的“买家”“商家”表示业务身份，不表示已经完成登录。

### （三）用例文字描述

以下描述与图中的 15 个用例一一对应，按公共功能、买家交易、商家经营编号。主流程描述一次典型的成功交互，备选流程描述正常分支，异常流程描述无法完成操作的情形；A、E 编号在各用例内独立使用。

本节着重说明参与者的操作与系统应产生的结果。登录是受保护操作的前置条件，无需在每个用例中重复一次完整登录流程。

#### 用例：浏览与搜索商品

**ID**：UC-001

**Actor**：访客、商城用户（买家、商家）

**前置条件**：无需登录。

**主流程**：

1. Actor 进入商品页面，浏览列表，或输入关键词、选择品类进行查询。
2. 系统展示符合条件的已上架商品。
3. Actor 选择商品查看详情。
4. 系统展示商品说明、所属店铺、具体规格、当前售价和可售库存。

**后置条件**：Actor 获得公开商品信息，商品与库存不发生变更。

**备选流程**：

- A1：没有符合条件的商品 → 显示空列表，Actor 可以调整查询条件。
- A2：Actor 只浏览列表 → 无需继续查看详情。

**异常流程**：

- E1：查询条件不合法 → 提示修正输入。
- E2：查看详情时商品不存在或已下架 → 提示商品不可访问。

#### 用例：注册买家账号

**ID**：UC-002

**Actor**：访客

**前置条件**：系统已开启公开注册功能。

**主流程**：

1. 访客填写用户名和密码并提交注册。
2. 系统检查输入是否符合要求，以及用户名是否已被使用。
3. 系统创建买家账号，妥善保存登录凭据。
4. 系统告知注册成功，访客可以使用新账号登录。

**后置条件**：成功时新增买家账号；失败时不留下未完成的账号记录。注册不等于已经登录，也不创建商家账号或店铺。

**异常流程**：

- E1：公开注册已关闭 → 提示当前不允许注册。
- E2：用户名或密码不符合要求 → 提示修改输入。
- E3：用户名已被使用 → 提示更换用户名。

#### 用例：登录系统

**ID**：UC-003

**Actor**：商城用户（买家、商家）

**前置条件**：Actor 已有账号；商家账号由系统初始化建立。

**主流程**：

1. Actor 输入用户名和密码并提交登录。
2. 系统核对账号与密码，确认账号对应的角色。
3. 系统建立登录身份，允许 Actor 使用相应角色的功能。

**后置条件**：成功时 Actor 处于已登录状态，账号角色保持不变；失败时不建立新的登录身份。

**异常流程**：

- E1：账号不存在或密码错误 → 提示用户名或密码错误。
- E2：输入不合法或登录服务暂不可用 → 提示修正输入或稍后重试。

#### 用例：咨询商品选购建议

**ID**：UC-004

**Actor**：商城用户（买家、商家）

**前置条件**：Actor 已登录。

**主流程**：

1. Actor 提出选购问题，可以补充预算和品类。
2. 系统根据问题及明确填写的条件，查找符合要求、已上架且有库存的商品规格，并查阅公开资料。
3. 系统依据查得的信息组织选购建议。
4. 系统展示回答、推荐商品及引用资料，供 Actor 判断。

**后置条件**：Actor 获得有数据依据的选购建议；系统不代为下单，也不修改购物车、订单或库存。

**备选流程**：

- A1：没有合适商品 → 说明未找到符合条件的商品，Actor 可调整需求。
- A2：智能回答暂不可用但商品和资料仍可读取 → 提供基础建议并说明当前回答受限。

**异常流程**：

- E1：登录身份失效 → 提示重新登录。
- E2：问题或筛选条件不符合要求 → 提示修正输入。
- E3：必要商品数据无法读取 → 提示服务暂不可用。

#### 用例：管理购物车

**ID**：UC-005

**Actor**：买家

**前置条件**：买家已登录；新增或设置条目时，需选择具体商品规格（SKU）和目标数量。

**主流程**：

1. 买家选择一个 SKU，填写希望购买的数量。
2. 系统检查商品是否可购买、数量是否合适，以及购物车是否已达容量上限。
3. 系统新增该条目，或将已有条目的数量设置为本次填写的值。
4. 买家查看更新后的购物车，其中显示商品规格、数量、当前价格和所属店铺。

**后置条件**：成功时本人购物车按要求更新；失败时本次修改不生效。加入购物车不扣库存，也不锁定成交价格。

**备选流程**：

- A1：买家仅查看购物车 → 展示本人条目，购物车为空时显示空列表。
- A2：买家移除条目 → 移除本人对应条目；重复移除不会产生额外影响。
- A3：对同一 SKU 重复设置数量为 2 → 最终仍为 2，不累加为 4。
- A4：已有条目的商品后来下架 → 仍可查看失效状态并移除。

**异常流程**：

- E1：不是已登录买家 → 拒绝操作。
- E2：数量不在 1—99 范围内，或超过当前可售库存 → 提示调整数量。
- E3：商品或 SKU 不可用，或新增后购物车超过 50 种 SKU → 拒绝本次设置并说明原因。

#### 用例：提交订单

**ID**：UC-006

**Actor**：买家

**前置条件**：买家已登录；首次提交时，所选 SKU 位于本人购物车中且属于同一家店铺，买家已填写收货信息。

**主流程**：

1. 买家选定同一家店铺的购物车条目，确认收货信息并提交订单。
2. 系统确认买家身份，判断是否已处理过同一次下单。
3. 系统核对所选条目、实际数量、商品上架状态和库存。
4. 系统按当前售价和购物车数量计算成交金额。
5. 系统建立待支付订单及商品明细，保存收货信息与成交时的名称、规格、单价和数量。
6. 系统扣减对应库存，移除已经结算的购物车条目，向买家展示订单结果。

**后置条件**：成功时生成一笔待支付订单，成交记录、库存和购物车同步更新；失败时不留下订单已建立而库存或购物车仅部分更新的结果。

**备选流程**：

- A1：因网络问题重复提交同一次下单 → 返回原订单，不再次创建订单或扣减库存。

**异常流程**：

- E1：不是已登录买家 → 拒绝下单。
- E2：所选商品跨店铺、收货信息不合法或所选条目已不在购物车中 → 提示重新确认。
- E3：商品已下架或库存不足 → 提示刷新购物车后调整选择。
- E4：将不同商品选择或收货信息当作原下单请求重试 → 拒绝作为同一次下单处理。
- E5：未收到明确下单结果 → 应确认原下单结果，避免误将重试当作一次新购买。

#### 用例：查看本人订单

**ID**：UC-007

**Actor**：买家

**前置条件**：买家已登录。

**主流程**：

1. 买家进入本人订单页面。
2. 系统展示该买家的订单列表。
3. 买家选择一笔订单查看详情。
4. 系统展示订单状态、成交金额、收货信息和成交时的商品明细。

**后置条件**：买家获得本人订单信息；查询不改变订单状态、金额或库存。

**备选流程**：

- A1：尚无订单 → 显示空列表。
- A2：只查看列表 → 无需继续查看详情。

**异常流程**：

- E1：不是已登录买家 → 拒绝查询。
- E2：订单不存在或不属于当前买家 → 提示订单不可访问，不展示他人订单。

#### 用例：支付订单

**ID**：UC-008

**Actor**：买家

**前置条件**：买家已登录；首次支付的订单属于本人，且处于待支付状态。

**主流程**：

1. 买家选择本人待支付订单，发起模拟支付。
2. 系统核对订单归属和当前状态。
3. 系统将订单标记为已支付，记录支付时间。
4. 系统展示支付后的订单信息。

**后置条件**：成功时订单变为已支付；不再次扣库存，不修改成交金额，也不发生真实资金扣款。失败时本次操作不改变订单。

**备选流程**：

- A1：订单已支付，或已继续进入发货、完成阶段 → 返回当前结果，不重复支付或改写原支付时间。

**异常流程**：

- E1：身份不符、订单不存在或不属于本人 → 拒绝操作。
- E2：订单已取消 → 提示当前状态不能支付。

#### 用例：取消订单

**ID**：UC-009

**Actor**：买家

**前置条件**：买家已登录；首次取消的订单属于本人，且处于待支付状态。

**主流程**：

1. 买家选择本人待支付订单，发起取消。
2. 系统核对订单归属和当前状态。
3. 系统按原订单明细归还库存，将订单标记为已取消。
4. 系统展示取消结果。

**后置条件**：成功时订单为已取消，原扣减库存仅归还一次；保留历史订单，不自动恢复购物车。失败时不留下取消状态与库存归还不一致的结果。

**备选流程**：

- A1：订单已经取消 → 返回当前结果，不再次归还库存。

**异常流程**：

- E1：身份不符、订单不存在或不属于本人 → 拒绝操作。
- E2：订单已支付、已发货或已完成 → 提示不能取消；退款和退货不属于本用例。

#### 用例：确认收货

**ID**：UC-010

**Actor**：买家

**前置条件**：买家已登录；首次确认收货的订单属于本人，且处于已发货状态。

**主流程**：

1. 买家选择本人已发货订单，确认收货。
2. 系统核对订单归属和当前状态。
3. 系统将订单标记为已完成，并展示结果。

**后置条件**：成功时订单变为已完成；失败时本次操作不改变订单。确认收货不改变库存和成交金额。

**备选流程**：

- A1：订单已完成 → 返回当前结果，不重复处理。

**异常流程**：

- E1：身份不符、订单不存在或不属于本人 → 拒绝操作。
- E2：订单尚未发货或已经取消 → 提示当前状态不能确认收货。

#### 用例：管理本店商品

**ID**：UC-011

**Actor**：商家

**前置条件**：商家已登录且关联有效店铺；编辑已有商品或 SKU 时，目标须属于本店。

**主流程**：

1. 商家进入商品管理页面，选择创建商品，填写名称、品类、说明和上架状态。
2. 商家填写至少一种可售规格，以及该规格的售价和库存。
3. 系统检查输入，并将商品及规格保存到当前店铺。
4. 商家查看更新后的本店商品列表。

**后置条件**：成功时本店商品及规格按操作更新；失败时不留下本次创建的半成品。其他店铺商品和历史订单成交信息不受影响。

**备选流程**：

- A1：仅查看商品 → 展示本店商品和规格，不修改数据。
- A2：编辑已有商品 → 修改介绍或上架状态。
- A3：新增或编辑 SKU → 维护规格、售价与库存；输入库存 12 表示设为 12，不是增加 12。

**异常流程**：

- E1：不是关联有效店铺的已登录商家 → 拒绝操作。
- E2：商品或 SKU 不存在或不属于本店 → 拒绝访问。
- E3：商品未提供规格、售价不大于 0、库存为负或其他输入不合法 → 提示修正。
- E4：同一商品内规格编码重复，或新增后超过 20 个 SKU → 拒绝新增。

#### 用例：查看本店订单

**ID**：UC-012

**Actor**：商家

**前置条件**：商家已登录且关联有效店铺。

**主流程**：

1. 商家进入本店订单页面。
2. 系统根据登录身份确定店铺，展示该店铺的订单。
3. 商家查看订单状态、收货信息、成交金额和商品明细，了解待处理订单。

**后置条件**：商家获得本店订单信息；查询不修改订单和库存，也不展示其他店铺订单。

**备选流程**：

- A1：本店尚无订单 → 显示空列表。

**异常流程**：

- E1：不是关联有效店铺的已登录商家 → 拒绝查询。
- E2：订单读取失败 → 提示查询失败，不将其显示为暂无订单。

#### 用例：处理订单发货

**ID**：UC-013

**Actor**：商家

**前置条件**：商家已登录且关联有效店铺；首次发货的订单属于本店，且处于已支付状态。

**主流程**：

1. 商家选择本店已支付订单，发起模拟发货。
2. 系统核对订单店铺归属和当前状态。
3. 系统将订单标记为已发货，并展示结果。

**后置条件**：成功时订单变为已发货，买家之后可以确认收货；不再次扣库存，也不修改成交金额。本版本不调用真实物流平台。

**备选流程**：

- A1：订单已处于已发货状态 → 返回当前结果，不重复处理。

**异常流程**：

- E1：身份不符、订单不存在或不属于本店 → 拒绝操作。
- E2：订单待支付、已取消或已完成 → 提示当前状态不能发货。

#### 用例：查看本店销售统计

**ID**：UC-014

**Actor**：商家

**前置条件**：商家已登录且关联有效店铺。

**主流程**：

1. 商家选择要查看的统计天数。
2. 系统确定当前店铺及统计时间范围，查找该范围内已支付的订单，包括之后已发货或已完成的订单。
3. 系统汇总订单数、销售额、客单价、每日变化和热销商品，并与前一个等长周期比较。
4. 商家查看统计结果及对应时间范围。

**后置条件**：商家获得本店销售表现；查询不修改原始交易记录，统计数值来自实际订单。

**备选流程**：

- A1：未选择天数 → 默认查看此前 7 个完整 UTC 日，不含当天。
- A2：本期没有符合条件的订单 → 显示零值与空排行。
- A3：上期销售额为 0 → 说明增长率无法按通常公式计算。

**异常流程**：

- E1：不是关联有效店铺的已登录商家 → 拒绝查询。
- E2：统计天数不在 1—90 范围内 → 提示调整范围。
- E3：统计读取失败 → 提示查询失败，不用零值代替失败结果。

#### 用例：获取本店经营分析

**ID**：UC-015

**Actor**：商家

**前置条件**：商家已登录且关联有效店铺。

**主流程**：

1. 商家选择分析时段，提交经营分析请求。
2. 系统读取当前店铺相应时段的销售统计，与 UC-014 使用相同的数据口径。
3. 系统根据统计结果组织经营观察、可能原因及后续检查建议。
4. 商家结合数值与解释，判断后续经营动作。

**后置条件**：商家获得本店统计及其解释；原因假设与已确认事实分别表达，系统不自动修改商品、库存或订单。

**备选流程**：

- A1：本期无成交或缺乏可比较的上期数据 → 说明数据限制，不编造经营原因。
- A2：智能分析暂不可用但统计仍可读取 → 提供基础统计解释并说明当前回答受限。

**异常流程**：

- E1：不是关联有效店铺的已登录商家 → 拒绝请求。
- E2：分析时段不合法 → 提示修正输入。
- E3：必要统计数据无法读取 → 提示分析失败，不凭空生成经营结论。

## 三、从用例中分析数据需求

通过用例，我们已经知道系统需要完成哪些操作。接下来要问：为了完成这些操作，系统必须记住什么？下面以购物和经营过程为线索，逐步整理需要在下一章建模的对象及其关系。

### （一）谁在购买，谁在经营？

注册和登录说明系统需要保存账号信息，并区分买家与商家。访客尚未登录，并不因此需要建立一条“访客账号”记录。

商家不仅拥有账号，还经营一个店铺。账号用来识别使用者，店铺用来组织商品、接收订单和归集销售数据，因此两者是不同的业务概念。本版本中，一个商家账号对应一个店铺；买家账号不经营店铺。

由此可以识别出**用户和店铺**。后续还要表达商品属于哪个店铺、订单由哪个买家向哪个店铺提交，才能支撑“查看本人订单”和“查看本店订单”。

### （二）买家购买的是商品，还是商品的某一种规格？

以一款笔记本电脑为例，名称、品类和介绍属于商品的共同信息；“16GB / 512GB”和“32GB / 1TB”则是两种可售规格，各自具有售价和库存。这样的具体可售规格在项目中称为 **SKU**。

如果只记录商品，就无法准确回答买家选了哪一种配置、应该付多少钱、应扣减哪一份库存。因此需要区分**商品和 SKU**：商品组织共同介绍，SKU 表达具体卖什么以及当前售价、库存。

这也解释了为什么购物车和订单明细最终指向 SKU：买家加入购物车的是一种明确的规格，而不是一个尚未确定配置的商品名称。

### （三）购物车与订单为什么需要分开？

购物车表达购买意愿，买家可以反复改变数量或移除条目。为了再次打开页面时恢复选择，系统需要记住“哪个买家、选择哪个 SKU、数量是多少”，这形成了**购物车条目**。

同一买家对同一 SKU 调整数量，是修改同一条购买意愿记录。加入购物车不扣库存，也不固定价格；正式下单时才重新确认是否有货和成交金额。

订单则记录已经提交的交易。下单后，即使购物车中的所选条目被移除，买家和商家仍须能够查询和处理这笔订单。因此，**订单必须独立于购物车保存**。

### （四）一笔订单为什么还需要订单明细？

假设买家向同一家店铺购买两种规格：一件背包和两件收纳包。

整笔订单共享买家、店铺、收货信息、下单时间、订单状态和总金额；但每种规格的名称、单价和数量不同。需要将“整笔交易的信息”与“每项购买内容的信息”分开记录，形成**订单和订单明细**。

| 信息层次 | 需要回答的问题 | 例子 |
| --- | --- | --- |
| 订单 | 谁向哪家店购买、寄到哪里、何时下单、总额多少、进展如何？ | 同一买家向同一家店提交一笔订单，共用一份收货信息 |
| 订单明细 | 这一笔订单分别买了什么规格、每种多少件、成交单价多少？ | 背包规格一件，收纳包规格两件，分别记录单价与数量 |

每笔订单至少有一项购买明细，总金额由各明细的成交单价与数量计算得到。由于本版本按店铺结算，一笔订单只需明确归属一个店铺；跨店购买会形成不同订单。

### （五）历史订单为什么不能直接显示商品的最新信息？

假设买家今天以 2899 元购买某规格，明天商家将它改名并调价到 3099 元。如果查询订单时只读取商品当前的信息，就会把历史交易错误地展示成新价格。

因此，订单明细需要保留成交当时的商品名称、规格、单价和数量，这些信息称为**成交快照**。收货信息也按本次下单时填写的内容保存。

商品目录描述“现在卖什么、现在多少钱”，成交快照描述“当时买了什么、当时多少钱”。理解这个时间差异，才能在下一章解释为什么订单明细既关联 SKU，又保存一份成交信息。

### （六）订单还需要记住哪些变化？

支付、取消、发货和收货都在处理同一笔订单，因此系统需要记录订单当前处于哪个阶段。其基本变化为：

```text
提交订单 → 待支付 → 已支付 → 已发货 → 已完成
              └→ 已取消
```

下单时扣库存，取消待支付订单时归还库存；支付、发货和收货不再次扣库存。状态让系统能够判断当前允许哪种操作，而明细中的 SKU 和数量让系统知道应该扣减或归还哪些库存。

系统还要区分下单时间与支付时间：一笔订单今天提交、明天支付时，销售统计需要按照实际支付时间归入对应时段。查询本人订单需要买家归属，查询本店订单与销售统计需要店铺归属。

网络问题还可能让买家重复提交同一次下单。系统需要记住这次下单的标识及其对应内容，从而分辨“重试原请求”和“再次购买”。下一章中的幂等标识就是为这一需求准备的；具体处理方式在第 07 章学习。

### （七）统计与 AI 是否需要另外建立一套交易数据？

销售额、支付订单数和热销商品都可以从已有订单及明细中计算。本版本直接根据这些交易记录生成统计结果，经营分析再使用同一份统计提供解释，因此不需要为了两个展示入口各自保存一套销售事实。

导购则读取商品、SKU 和公开说明资料。商品价格与库存来自数据库，公开文本资料在后续 AI 章节中单独组织。出现一个用例，不意味着就要建立一张同名数据表；是否需要持久化，应看它是否产生了需要独立保存的业务信息。

## 四、系统总体结构与下一章的准备

### （一）这些操作由系统的哪些部分完成？

上一章已经认识了浏览器、后端和数据库的运行关系。结合本章业务，可以进一步明确它们的大体作用：

| 系统部分 | 在本项目中的作用 |
| --- | --- |
| 前端页面（Vue） | 提供商品展示、购物车、订单与商家操作入口，收集输入并展示结果 |
| 后端应用（FastAPI） | 识别使用者、判断操作是否允许、处理购物与经营业务，组织查询和 AI 回答 |
| 数据库（MySQL） | 持久保存账号、店铺、商品规格、购买意愿与交易记录 |
| AI 辅助能力 | 由后端组织商品查询、资料查阅与销售统计解释，结果通过页面展示 |

一次操作通常由页面发起，经后端判断和处理后读写数据库，再把结果展示给使用者。后端可以按账号、商品、购物车、订单、统计和 AI 划分功能；本阶段先理解这些功能边界，后续章节会逐步建立具体代码。

### （二）带着哪些业务对象进入第 02 章？

通过前面的分析，已经能够说明以下七类数据为什么存在：

| 业务对象 | 一条记录表达的业务事实 | 主要关系 |
| --- | --- | --- |
| 用户 | 一个可以登录的账号及其角色 | 买家拥有购物车条目并提交订单；商家经营店铺 |
| 店铺 | 一个商家的经营主体 | 属于商家，拥有商品并接收订单 |
| 商品 | 店铺中的一种商品及其共同介绍 | 属于店铺，包含具体可售规格 |
| SKU | 商品的一种可售规格及其当前售价、库存 | 属于商品，被购物车条目和订单明细引用 |
| 购物车条目 | 某买家打算购买某 SKU 的数量 | 关联买家和 SKU |
| 订单 | 某买家向某店铺提交的一次交易 | 关联买家、店铺，包含购买明细 |
| 订单明细 | 某笔订单中一个 SKU 的成交内容 | 关联订单和 SKU，保留成交快照 |

这些对象来自对业务信息的区分，不是简单地把用例名称转换成表名。下一章将继续确定它们的关系数量、完整字段与约束，形成 E-R 图和逻辑模型；第 03 章再将模型写成建表 SQL。

阅读第 02 章前，应能结合一个购物例子说明：

1. 为什么账号与店铺、商品与 SKU 需要区分？
2. 为什么提交订单后，不能只依赖购物车保存交易？
3. 为什么订单要有明细，明细还要保留成交时的信息？
4. 为什么订单需要记录买家、店铺、状态、下单时间和支付时间？

理解了这些问题，就可以沿着“业务事实 → 数据对象及关系 → 字段与约束”的顺序，继续学习数据库设计。
